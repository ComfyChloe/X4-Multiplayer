PROBLEM AND CHANGE
7.2 starts independently generated worlds, so ordinary station identity/positions
can differ. A fixed numeric seed was investigated first, as requested. Two fresh
native Linux worlds with seed276944566 produced1381 and1382 stations:1335 tuples
(code,macro,owner,sector) agreed exactly, but46/47 identities were absent/extra.
Both actual native save headers confirm that seed. Equal numeric seed alone is
therefore NOT accepted as a complete initial-universe solution. Raw failures stay
in work/x4-station-bootstrap/.local/evidence-218-withheld; no rows were filtered.

7.3 instead prepares ONE host-native pristine save before multiplayer fixtures.
2-PREPARE-WORLD launches an isolated world with gameplay adapters disabled,
checks actual active content in the engine, marks/saves save_010 and exits X4
through QuitGame after native completion. The launcher seals the completed bytes.
The regular server also serves authenticated snapshots over TCP45844. The guest
receives into a new private directory, verifies integrity/content/session, then
stages only its reserved journalled test slot. Both roles load the same snapshot
and pass the native MD marker/load-count gate before creating player fixtures.

The selected transport/gate implementation comes from reviewed PR18/a321b59.
The new distribution integration, capture/content checks and recovery ownership
are in this branch. PR31/9e05f11 supplies read-only catalog/origin diagnostics.
An actual native random seed3416042533 revealed that save headers use the unsigned
32-bit range. Origin/recipe descriptors now accept that range; unverified CLI
arguments above the previously bounded signed range remain refused.

RETAINED HARNESS FAILURES / CORRECTIONS
The first numeric capture finished natively, but its local wrapper used the wrong
header-format label and identified X4 only by comm, which later becomes Main().
The owned process was closed explicitly; subsequent execution used /proc/exe.

The initial p2 wrapper incorrectly read the PREVIOUS HOST LOG before Steam had
spawned the guest and prematurely reported readiness. That folder is explicitly
REJECTED in play-p2/harness-error.json. The actual already-launched guest's fresh
log was retained separately in play-p2-live. Its synthetic relay listened only
on localhost while the guest used its invited ZeroTier address; a task-owned
local UDP forwarder connected those interfaces. After that correction, fresh
p2 native role/control evidence passed. This is local synthetic-peer evidence,
NOT a remote ZeroTier or two-native gameplay test. The corrected validator
requires exact role, load/readiness order, native MD flags and own actor identity;
it rejects the stale host log forp2. No historical failure was overwritten.

BOUNDARIES
This aligns the STARTING universe. Independent station construction/destruction,
production/economy and arbitrary NPC decisions can still diverge as play advances.
Restart reloads the starting snapshot; campaign progress and absent-player catchup
are not implemented. Ongoing native-original/attachment experiments remain draft
and are not activated. Weapons/damage remain Claude-owned and unchanged.

The final clean packaged startup, when run, is recorded alongside the delivery;
it must not be inferred from these instrumented role captures. Native Windows,
Windows-host gameplay, simultaneous Windows/Linux play and full-world authority
remain outside this evidence. Prior accepted human radar/cargo/mission scenarios
were not replayed as new gameplay acceptance. Workshop account subscription state
was not independently queried; no selection or account writes were introduced.
