and a terminator. MassTrafficUpdateTask therefore has fallback name

These five body/name associations are strong static evidence. Only JobThread's
creation chain is traced here. For the four manager roles, singleton RTTI is not
proof of one running thread, stable lifetime, launch ordering or RNG ownership.
The body addresses are candidates for future verified instrumentation, not a
runtime hook installation contract. RegionManager's slot4 is not slot2.

JOB WORKERS: POOL SLOT, CAPACITY AND CREATION
In the observed manager-null startup path, global0x3daab88 is initialized with
32 contiguous JobThread objects at manager+0x50, stride0x20. The vtable store is
0x7300cc. The loop at0x730d60 writes indices0..31 to JobThread+0x1c; the naming
body reads precisely that field at0x1a54e05. This gives pool-slot labels within
this manager lifetime, independently of OS TID, pointer values or thread order.

Capacity32 is not the active count. At0x730d9b, startup calls sysconf(0x54),
identified as SC_NPROCESSORS_ONLN by this Linux host's sysconf definitions. The
unsigned count calculation subtracts2 when the result is greater than1, then
clamps to4..32 and stores manager+0x550. The two clamp constants were independently
read from0x2e248d0 and0x2e37640. Different hardware can select different worker
counts; matching names alone cannot establish equivalent job placement.

The launch loop at0x730e0f passes each pool object to wrapper0x1a52c50. That
wrapper passes the object and start thunk0x1a37230 to SDL_CreateThreadRuntime
at0x1a52c97. The thunk calls object.vtable[2] at0x1a37273, resolving to the
JobThread body above. The thunk also retains the wrapper pointer in FS:-0x2468;
this is thread-wrapper context, not a demonstrated RNG location.

Only this startup path was traced. Later object mutation, alternate construction,
restart/reuse and teardown remain unverified. Stable slot numbers do not prove
stable work assignment, draw ordering, identical results or cross-platform
determinism. A possible label is JobThread/<pool-slot>, with pool configuration
reported separately; adopting a seed/stream contract is still Ferrite's decision.

LINUX CLOCK / TLS BOUNDARY
Export GetCurrentGameTime at0xa41960 reads an eight-byte value at FS:-0x2728,
with an optional weak _ZTHN4XLib7CurTimeE initialization call. Both return paths
read the same location. This confirms a Linux thread-local CurTime anchor.
It does not identify the Linux RNG state, readiness flag, session seed or the
Windows TLS block layout used by PR59. Windows offsets+0x314/+0x318/+0x328 have
not been ported. No RNG state was read from a running process or modified.

EXCLUSIONS / VALIDATION
Exported WorkerThread0x269ece0 is an SLNet::FileListTransfer specialization and
is excluded from the engine JobThread role map. Direct pthread_create callsites
in vendor code do not establish engine creation; the verified job path uses SDL.
Nearest exported objdump labels inside stripped regions were not treated as
function names. Body starts were checked against the binary EH-frame index.

Astra independently re-read the pinned binary and verified all five RTTI/typeinfo/
vtable/body/name-reference/call-target chains. Each first32-byte signature has one
match in this file. The naming helper, JobThread field, initialization/launch
chain, count constants and both CurTime loads were independently inspected;
focused byte/pointer assertions passed. No gameplay or unchanged suite rerun was
needed for this report-only contribution. No native execution, attachment, hooks,
runtime seed changes, profile changes or package rebuild occurred.
