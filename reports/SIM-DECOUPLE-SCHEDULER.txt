X4 MULTIPLAYER - FIXED 60 HZ SIMULATION DECOUPLED FROM RENDERING (LINUX AGENT)
25 October 2026 | INTERNAL DEVELOPMENT | branch contrib/ferrite-sim-decouple

GOAL
Run X4's simulation in fixed 1/60 s steps that track wall time, while rendering only
occasionally (or never). Primary target: the headless Linux dedicated server, which
renders on the CPU (lavapipe) at 1-2 fps and today throttles the simulation to the
same rate. This is Stage 2 (bounded catch-up) plus a server render policy, built on
the Linux LD_PRELOAD agent (rust/x4mp-agent). Opt-in, off by default, exact-build
pinned (X4 9.00 build 23660954 Linux), fail-closed with full restore.

1. SIM/RENDER HANDSHAKE (Linux addresses; static analysis of bin-linux/X4)
Confidence: H = read in disassembly, M = inferred from structure, L = guess.

Main loop 0x72f250 (SDL event loop):                                        [H]
- frameInFlight byte 0x3d8d97b, initial value 1 in .data.
- While set: timed wait (16 ms) on semSimDone 0x3daab20 (0x72f751), then clear
  (0x72f7aa). Sync loading (appState 0x3daab04 bit 1) also clears it.
- When no SDL event is pending and frameInFlight is 0: FrameTick(*0x3daaaf0,
  loading) at 0x72fb16, then frameInFlight = 1 (0x72fb1b).
- Because frameInFlight starts at 1, the first wait consumes semSimDone's initial
  count. After that, each FrameTick is paired 1:1 with one simulation frame.
Semaphores: 0x1a23be0 Release(sem,n) and 0x1a23cc0 Wait (mutex +0, condvar +0x28,
count +0x58, max +0x5c); 0x1a23d90 TimedWait(ms).                            [H]

FrameTick 0x2024fc0 (main thread), non-loading path, in order:              [H]
 1. dt = TimerBase clock delta (0x1a3b880, CLOCK_MONOTONIC_RAW; first frame
    0.0333). If movie capture (0x4533d38): dt = [0x4533d40]. Otherwise
    dt = min(1.0, dt) (0x2025260).
 2. Under the TimerBase lock: gameTime += dt*speed, unpausedRealTime += dt if not
    paused, realTime += dt (0x2025280). This is the only time advance.
 3. 0x12029b0 with TLS view selector 0: publish the simulation's double-buffer
    indices to the main thread (0x3e7742c := 0x3e77430, 0x3d8e2a4 := 0x3d8e2a8)
    under the mutex at 0x3e4fec8.
 4. If FrameState+0x200: pre-render calls 0x224ceb0 / 0x218e2c0 (read #1).
 5. Renderer resource queue 0x21e8110; ProcessGraphicsStateChanges 0x2024070. If
    the frame was consumed: release semSimStart and return.
 6. Release semSimStart 0x3e59e20 (0x20251f6). The simulation frame starts now.
 7. If FrameState+0x200 (read #2, 0x2025208):
      render branch: BeginThreadedRenderFrame 0x2012510 (renderer frame advance
      0x21e78d0 + render dt from realTime), scene render 0x2024c20 (views from
      0x2022690 drawn by 0x20ab5e0 and finalized by 0x20965c0; movie screenshot
      0x21fc6a0), 0x21eddf0, PresentAndFrameLimit 0x2014900.
    else, the engine's no-render branch (0x2025430): renderer frame advance
      0x21e78d0 and 0x2022810 (the same view list, finalized by 0x20965c0
      without drawing). No present, no frame limiter.
FrameState: a 0x2f0-byte object, constructed by 0x201d800 (stored at 0xfd10d8),
which sets +0x200 = 1. A whole-binary scan of the 224 writes to [reg+0x200] found
none in a function that touches the FrameState global or its methods. FrameTick is
the only reader.                                                            [M-H]

MoveWorker 0x1212490 (TLS view selector 1):                                  [H]
 wait semSimStart; kick pathing (sem +0x70); sync TLS CurTime from gameTime;
 VBI slots 0..16 in order; audio accumulator; release semSimDone; signal
 MassTraffic/RegionManager.
- Slot 3 GameClient::Move 0xfeaff0 runs the universe update, then swaps the
  simulation's indices (0x12029b0 with selector 1: 0x3e77430 <-> 0x3d8e2a8, and
  vfunc +0x10 on the registered listeners at 0x3ea9000).
- Slot 10 GameRender::Move 0xfb0180 calls Render (vfunc +0x18) on the four
  render-bank handlers (VBI table +0x110..+0x128): UI, characters, GameClient.
Double buffer: yes. Component data has two copies selected by the view index, for
example `obj + idx*0x80 + 0x118` and `obj + idx*0x2c0 + 0x20` (0x12021e0 returns
the index for the calling thread). The simulation flips its index once per frame;
FrameTick publishes it to the render side once per FrameTick.               [H for
mechanism; M for exactly which copy each side reads]
Consequence: one render may overlap exactly ONE simulation frame. A second
simulation frame during the same render would flip the simulation back onto the
copy being rendered. The 1:1 handshake guarantees this, and it is the hard limit on
overlapping simulation with rendering.                                        [M-H]

Windows equivalents (bin/X4.exe RVAs, read for this note):                 [H]
FrameTick 0xfa2d70; render flag FrameState+0x1e4 (reads 0xfa339e, 0xfa3446);
no-render branch 0xfa346e = 0x104d460 + 0xfa4030 (Linux 0x21e78d0 + 0x2022810);
render branch 0xfa23a0 / 0xf9ff40 / 0xfa2ba0; dt clamp `minsd xmm6,[1.0]` at
0xfa32f3; capture override 0xfa32fb-0xfa3304 (Stage 1 NOPs the je at 0xfa3302);
FrameState global 0x6cf1578; frameInFlight byte 0x31c20cc (test 0x12ae9b5, set
0x12ae9d7); semSimStart 0x3d79150, semSimDone 0x3d79108.

2. CHOSEN DESIGN AND WHY IT IS SAFE
Rejected: extra "advance time + release semSimStart + wait semSimDone" cycles at
the main-loop call site. That needs code on the main thread (a hook), duplicates
FrameTick's bookkeeping (publish, renderer resource queue, graphics-state handling)
by hand, and leaves the renderer's frame counter (0x21e78d0) behind the
simulation's slot-10 output.

Chosen: keep the engine's own 1:1 FrameTick/simulation pairing unchanged; one
FrameTick = one fixed step. Per step, choose whether the NEXT FrameTick renders by
writing the FrameState render flag, which selects the engine's existing
no-render branch. Pace steps against wall time by sleeping on the MoveWorker. No
semaphore is touched and no engine function is called.
- Render lists stay consistent. Each simulation frame's slot-10 output is consumed
  by exactly one FrameTick, through the render branch or the no-render branch. Both
  advance the renderer frame (0x21e78d0) once and finalize every view (0x20965c0)
  once. The no-render branch omits only drawing, the screenshot and the present.
- No skipped list swap. The publish (step 3) and the semaphore release run on every
  FrameTick in both branches. Nothing that swaps is skipped.
- Swapchain. The no-render branch never acquires or presents an image, so it cannot
  leave a half-used image behind. The next render branch is an ordinary frame with a
  larger render dt.
- No torn decision. The flag is written only from VBI slot 13 while frameInFlight
  == 1. Then the main thread has returned from FrameTick and cannot re-enter it
  before this simulation frame releases semSimDone. Both reads in the next
  FrameTick therefore see the same value, and the write happens-before them through
  the semaphore's mutex. If the main thread is still inside FrameTick (a render), slot 13
  waits for it, bounded by X4MP_SCHED_WAIT_MS. This costs no throughput: the 1:1 handshake
  already stops this simulation frame from finishing before that render does. On
  timeout, nothing is written and the old value stays (always consistent).
- Fixed dt (Linux equivalent of the Windows capture-branch NOP). Two naturally
  aligned qwords at 0x2025260 and 0x2025268 are each replaced with one 8-byte
  compare-exchange:
    movsd xmm1,[rip->1.0]   becomes movsd xmm1,[rip->0x2e24578] (.rodata 1/60)
    minsd xmm1,xmm0         becomes a 4-byte NOP
  Every intermediate state is valid: after the first store dt = min(1/60, dt), and
  never 1.0. Restore runs in reverse order. Patching happens only while the main
  thread is parked (frameInFlight == 1). It uses mprotect r-x to rwx to r-x on page
  0x2025000 (X stays set for other threads on that page), plus best-effort
  membarrier(SYNC_CORE). No data write; the capture frame time is untouched.

3. BOUNDED CATCH-UP (src/scheduler.rs, unit-tested)
- Step clock: step k after the baseline may not be followed by the next FrameTick
  before epoch + k/60 s (exact integer arithmetic, no drift). Slot 13 sleeps until
  then.
- Behind (one or more whole steps late): skip renders, FrameTicks run back to back
  at simulation speed.
- Max steps per render: after X4MP_SCHED_MAX_CATCHUP consecutive skipped renders
  while behind, force one render (clients keep a picture).
- Spiral-of-death guard: lateness above X4MP_SCHED_MAX_LAG_MS is dropped (the
  epoch moves forward) and logged as dropped_ms. Game time then runs slower than
  wall time instead of chasing an unbounded debt.
- Loading (VBI loading flag) or a FrameTick without time advance (end of load):
  render, rebaseline (a load is not debt).
- Save: RequestSaveGame's tempPauseCount (3-frame countdown) renders whenever the
  interval allows, even while behind; the save hitch itself is covered by the lag
  guard.
- Pause (speed 0) / SETA (speed <= 6): no rule needed. The step clock stays 60 Hz
  wall time; game time advances speed/60 per step and stays monotonic.
- Time guard per step: realTime must advance by exactly 1/60 (or 0 at load end),
  otherwise FAULT and full restore. Game time must advance by speed/60, with speed
  as seen in the previous step; steps that match count as `exact`, others as
  `irregular` (logged, not fatal: SetGameTime, or speed written after slot 13).

4. SERVER MODE
- X4MP_RENDER_INTERVAL_MS=N renders at most every N ms, and only when the step clock
  is on time. Simulation runs at 60 Hz in between.
- X4MP_RENDER_INTERVAL_MS=never takes the no-render branch on every FrameTick. The
  engine still advances the renderer frame and finalizes views every step.
  Statically this is consistent. Whether every subsystem tolerates hours without a
  rendered frame (for example fade or render-target consumers) is unproven:
  test it natively after the interval modes.
- Throughput limit (inherent, see section 1): during one render only one simulation
  step runs. Game/wall reaches 1.0 only when
      render_cost / interval + step_cost * 60 < 1.
  For example, a 700 ms lavapipe render every 2000 ms leaves 1.3 s for 119 steps,
  which needs at most about 10 ms per step. 1-2 renders/s at 700 ms each cannot also
  give a ratio of 0.95. Choose the interval from the measured max_wait_ms (about the
  render time).

5. IMPLEMENTATION (rust/x4mp-agent)
- src/scheduler.rs: platform-independent policy (Scheduler, check_step,
  slot13_step generic over an Engine trait, SCHED log line), with unit tests.
- src/sched_live.rs: Linux live side (admission, patch/restore, live Engine,
  statistics, restore protocol).
- src/agent.rs: calls the scheduler at the end of the slot-13 callback (including
  loading frames). disarm() restores first: in-slot on the MoveWorker; otherwise
  the worker asks slot 13 and restores itself after 3 s. Per-second SCHED lines;
  ARMED / REFUSED / FAULT / RESTORED events.
- src/config.rs: X4MP_SCHED, X4MP_RENDER_INTERVAL_MS, X4MP_SCHED_MAX_CATCHUP,
  X4MP_SCHED_MAX_LAG_MS, X4MP_SCHED_WAIT_MS (bounded; any invalid value refuses the
  whole agent).
- src/pinned.rs: 8 new sites (24 total), plus the scheduler data addresses and
  patch bytes. x4mp-sigcheck also checks the original dt bytes, the 1/60
  constant and frameInFlight's initial value in the file.
- tests/sim_harness.rs: real threads. A fake main loop and FrameTick and a fake
  MoveWorker, joined by semSimStart/semSimDone with the engine's initial counts,
  drive the real slot13_step.
Admission (first non-loading slot-13 call after the observer arms) requires:
FrameState mapped with render flag 1, movie capture off, the 1/60 constant, four
live site hashes, original dt bytes, the code page r-x, and the main thread parked.
A refusal leaves the engine untouched and keeps the observer. A runtime guard
failure (FrameState pointer, capture on, dt bytes, realTime step, a foreign
render-flag write, poisoned state) restores and disarms the whole agent.

6. VALIDATION (offline only; no native X4 run by this task)
WSL Ubuntu 24.04, cargo 1.99.1: cargo test -p x4mp-agent: 32 unit + 4 harness
PASS (3 consecutive runs). cargo clippy --all-targets -D warnings: clean.
x4mp-sigcheck on x4-re/bin-linux/X4: build-id + 24 sites PASS, plus the scheduler
preconditions. Harness results: rare 150 ms renders every 500 ms give game/wall
0.93-1.03 with all steps exact; never-render steps at 55-61.5/s; a 25 ms render
with interval 0 gives 15-40 renders/s at 60 Hz simulation; overload drops time
(>500 ms) with skip runs <= 10. Zero torn decisions, zero writes while the main
thread was inside FrameTick, no render overlapping two simulation frames.

7. NATIVE TEST PROCEDURE (lead session, VPS)
Deploy the new libx4mp_agent.so at the supervisor's configured engine_agent path.
X4 inherits the supervisor's environment, so set the variables there (systemd
unit Environment= or the launching shell); the supervisor adds LD_PRELOAD,
X4MP_AGENT=1 and X4MP_AGENT_LOG=<work>/engine-agent.log.
 a) Baseline (observer only): no X4MP_SCHED. Expect CADENCE fps of about 1-2 and a
    dgame/dreal ratio below 1.
 b) X4MP_SCHED=fixed60 X4MP_RENDER_INTERVAL_MS=2000 X4MP_SCHED_MAX_CATCHUP=600
    X4MP_SCHED_MAX_LAG_MS=1000
 c) Same with X4MP_RENDER_INTERVAL_MS=1000, then 500.
 d) X4MP_RENDER_INTERVAL_MS=never (run at least 30 min, with a client connected).
Expected log lines, in order:
  X4MP_AGENT VERIFIED build=23660954 version=9.00 (611726) sites=24 pid=...
  X4MP_AGENT SCHED CONFIG mode=fixed60 render=IntervalMs(2000) max_catchup_steps=600 ...
  X4MP_AGENT ARMED slot=13 table=0x...
  X4MP_AGENT SCHED ARMED dt=1/60 patch=0x2025260,0x2025268 render_flag=FrameState+0x200
  then once per second: CADENCE ... tls_dt=0.016667 ...
  and: X4MP_AGENT SCHED state=armed sps=60.00 rps=0.50 game_wall=1.0000 ...
Pass criteria (steady state, speed 1, unpaused, after the first 30 s):
  - every CADENCE tls_dt = 0.016667 (fixed step); SCHED `irregular` stays 0 apart
    from load/save moments; no FAULT;
  - sps between 59 and 61 and game_wall >= 0.95 at the chosen interval; rps at most
    1000/interval; ddropped_ms 0 except for saves or loads;
  - max_wait_ms is about the render cost. Choose the interval so that render_cost /
    interval + (step cost * 60) < 0.9;
  - clients see normal motion. Pause gives game_wall 0 with sps still 60; SETA gives
    game_wall_per_speed of about 1.0;
  - a save (manual or scheduled) produces a single ddropped_ms spike, then catch-up.
Disarm and restore:
  - touch <work>/engine-agent.log.disarm (default X4MP_AGENT_DISARM_FILE). Within
    about 1 s expect `X4MP_AGENT DISARMED reason=disarm_file_present sched=restored
    ... restore=slot` (or restore=worker during loading). Afterwards the dt bytes
    and the render flag are back to the original, and X4 runs as before.
  - or restart X4 without X4MP_SCHED (everything is in memory only).
  - FAIL means any FAULT line, REFUSED (the line gives the reason), a crash, or
    game_wall below 0.9 at an interval where max_wait_ms/interval < 0.5.

8. RISKS / LIMITS
- One simulation step per render is a hard limit (double buffer). With expensive
  renders the interval must be long enough (section 4). Must stay single-step: the
  FrameTick/semaphore pairing itself, and every FrameTick's time advance and publish.
- fs+0x200 sole-writer evidence is a static scan (M-H). A foreign write is detected
  (render flag not equal to the last value written) and faults with a restore.
- Pre-render calls 0x224ceb0 / 0x218e2c0 and the present are skipped on no-render
  frames, as in the engine's own no-render frames. Their exact purpose is
  unidentified (M).
- `never` mode is statically consistent but natively unproven (section 4).
- Render dt (realTime since the last render) becomes large on render frames
  (seconds). Render-side animation steps are coarse; no simulation effect seen.
- Cross-modifying code: aligned atomic 8-byte stores, applied while the main
  thread is parked, plus membarrier SYNC_CORE when available. A restore from the
  worker fallback (no safe window) relies on store atomicity alone.
- Lua UI onUpdate, input and Steam run once per step (60 Hz), not per render. UI
  scripts that assume one update per presented frame were not audited.
- Fixed timing reduces divergence; it is not determinism (RNG, attention, worker
  races and FP differences remain).

9. WINDOWS PORT NOTE (fixedtick.c; not implemented here)
Same design maps 1:1. Keep Stage 1's dt (NOP je 0xfa3302 + capture frame time
1/60). Then in the slot-5 callback:
  - wait (bounded) for byte [0x31c20cc] == 1 (main thread out of FrameTick);
  - write byte [*(0x6cf1578) + 0x1e4] = render ? 1 : 0 (initial value and
    sole-writer property must be re-verified on Windows the same way);
  - pace with the same Scheduler logic (port scheduler.rs or call it via FFI).
New Windows sites: FrameTick 0xfa3390-0xfa3489 (both flag reads, no-render
branch), main loop 0x12ae9b5-0x12ae9de, and the FrameState constructor writing +0x1e4.
The Stage 1 admission rule "limiter at 60" no longer applies: no-render frames skip
PresentAndFrameLimit, and pacing moves into the callback. Not implemented because
the slot-5 FFI and the Windows tests need their own native run; Linux was the
priority.
