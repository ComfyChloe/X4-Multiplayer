SHARED HOST SAVE — INTERNAL IMPLEMENTATION AND NATIVE FEASIBILITY
20 October 2026

The 7.1.1 playtest confirms that independent custom_creative starts do not give
the players a shared universe. Ordinary station positions differ. Copying a
native host snapshot can align the initial world, but is only the first step
towards ongoing host authority.

IMPLEMENTED, NOT ENABLED IN GAMEPLAY
x4lan/seed.py seals an immutable native snapshot and its session/build/content
manifest. A bounded TCP stream transfers the exact bytes, authenticates the
request and manifest using a nonce and the private session key, and verifies
SHA-256 before publishing the received bundle. A different seed, game build,
extension set or mod digest is rejected. There is no network-supplied filename.
Partial transfers and corrupt data do not produce a completed bundle.

The opt-in staging operation copies a verified bundle into save_010 of an empty
isolated profile 45841. It refuses normal profiles, linked save directories,
existing save slots and reuse of completed bundle directories. The installed
copy does not share an inode with the immutable snapshot. The caller must check
that X4 is closed. This is a LAN/ZeroTier building block, not encrypted Internet
hosting, a public distribution change, or a complete launcher/admission flow.

NATIVE TEST
dev/native_seed_test.py, seed_probe.lua/xml and validate_native_seed.py run the
following explicitly separated steps with gameplay adapters disabled:
  1. Create a new disposable world and persist a random MD session marker.
  2. Pause, enumerate native stations and ask X4 to save the world.
  3. Close X4, seal the completed native save, transfer over real loopback TCP
     and verify the received bytes.
  4. Copy into the empty isolated test slot, launch and actually load that slot.
  5. Verify the saved MD marker and independently enumerate native stations.
  6. Close X4, preserve the evidence, verify preexisting save bytes/timestamps,
     and remove only the unchanged test copy owned by this run.

OPTIONAL ADMISSION PROTOTYPE — NATIVE VALIDATION IN PROGRESS
The optional seed_game.lua / x4lan_seed.xml path blocks bubble setup and network
admission until the staged pristine snapshot has actually loaded. The seed ID
must match the relay's bubble/session identifier. Missing, wrong or already-used
worlds fail closed, as does a seed configuration selecting the legacy adapter.
The normal package configuration has no seed ID and does not enable this path.
No default launcher integration or new package has been prepared.

The first native attempt, retained under .local/evidence-137-withheld,
restored the correct saved marker but missed the Lua game-loaded notification
during UI reload. The gate stopped rather than starting an independent world.
The corrected design reads a persistent MD load count; it does not depend on
receiving that one Lua notification. A pristine capture has count zero and its
first native reload must report exactly one. The capture probe also verifies
the production marker before saving, rather than assuming event order.

The second native attempt, retained under .../gate-second, also stopped with the
right saved marker but an unexpected load counter at its first inspection. This
is a failure, not role-initialization acceptance. The next iteration permits a
zero counter to remain pending within the existing timeout and records native
load events explicitly; only counter one can admit the session.

Eleven LuaJIT gate regressions cover pending setup, missing files, wrong sessions,
wrong/used worlds, missed notifications, active reload and unsupported legacy
fallback. dev/native_seed_play_test.py installs one role at a time against the
same verified snapshot, and seed_play_probe.lua/xml read native pilot assignment,
all four authority flags and the number of shared Shuttles/markets. Native results
for the corrected gate are still pending.

A fresh session snapshot is taken before multiplayer fixture setup.
Both peers load that same uninitialized world, verify its marker and
create the agreed shared player roles. Reusing an already active host save
needs additional restoration of persisted host flags, cue state, pilot roles,
fixture references and request history. Blindly running fresh setup against
such a save risks duplicate ships/stations and guest host authority.

The launcher must check matching content,
stage only verified bytes and connect this with relay session admission. Mixed
or stale seeds must fail closed. Keep the existing internal pair unchanged while
this mode is incomplete.

Ongoing authority remains required after admission: orders must execute on the
host, ordinary NPC health/lifetimes and stations/economy must reconcile, and
competing guest simulation must be controlled without destroying mission
references. A common initial save alone does not fix these missing channels.
No joint Windows/Linux load, ongoing universe authority, late join, arbitrary
mission synchronization or production save/resume acceptance is claimed.
