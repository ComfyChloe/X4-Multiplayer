2. WHAT THE CURRENT CODE CONFLATES
---------------------------------
'p1' means three different things at once:
  (a) a human player (one ship, one lease, one X4 client);
  (b) the world authority (publishes WORLD/ECON/NPC/mission/quest, and decides LAN targets and NPC hits);
  (c) the machine that runs the relay (session_launcher: relay at 127.0.0.1).
'p2' means "the guest", and the code assumes there is exactly one.
Entity n is both "ship n" and "the ship slot n was born with". After a ship swap these come
apart: owners/pilot already track that, but the WORLD/AUTH/HGEN layouts and the Lua 3-own
still hard-code the pairing.

A dedicated server needs (b) without (a). N players need (a) with no limit of two.


3. PROPOSED INTERFACE
---------------------
One roster object is the only place that knows who exists. Every class in section 1 becomes a
question to it. It is language-neutral, so the Python relay, a Rust relay
(contrib/ferrite-rust-relay) and the Lua adapter implement the same contract.

  Roster
    players      ordered tuple of player ids        today ('p1', 'p2')
    authority    the world-authority id             today 'p1'; dedicated mode 'a0'
    ships        ordered tuple of player-ship ids   today (1, 2)
    born_owner   {ship: player}                     today {1: 'p1', 2: 'p2'}
    is_player(id), is_authority(id), is_ship(e), others(id) -> connected ids except id

  Ids
    player id   'p' + decimal 1..MAX_PLAYERS, wire pattern p[1-9][0-9]? (so p1/p2 bytes stay valid)
    authority   'a0': a peer with a lease and address but no player ship. In listen mode
                (today) the authority IS a player: authority == 'p1'.
    ship id     integer 1..MAX_SHIPS, a separate namespace from player ids. The 'p'+ship rewrite
                (coop.py COMMAND) goes away.
    LAN targets currently borrow victim ids 3-4. They move to their own namespace (a victim kind
                field, or a fixed offset such as 1001+) so that ship ids can grow.

  Replacement rules (each inventory site maps to exactly one)
    slot not in ('p1','p2')         -> not roster.is_player(slot)  [HELLO also accepts authority]
    slot == 'p1'  (publisher)       -> roster.is_authority(slot)
    slot == 'p2' / slot != 'p1'     -> not roster.is_authority(slot), with per-player state keyed
                                       by slot (universe interest, MREQ, mission pending)
    peers.get(other slot)           -> for other in roster.others(slot)
    peers.get('p1') (host lookup)   -> peers.get(roster.authority)
    peers.get('p2') (guest lookup)  -> iterate the non-authority players
    entity in (1, 2) / for (1, 2)   -> roster.is_ship(e) / for e in roster.ships
    world[(e-1)*3]                  -> a WORLD accessor keyed by ship id (layout carries count)
    owners = {1:'p1',2:'p2'}        -> owners = dict(roster.born_owner)
    Lua cfg.slot=='p1'/'p2'         -> X4LAN.roster:isAuthority(cfg.slot) / not ...
    Lua for e=1,2; ships[3-own]     -> for _,e in ipairs(roster.ships); own = owner lookup, a proxy
                                       for every other ship
    MD $ships.{1}/{2} literal       -> iterate $arena.$ships; index via $arena.$ships.indexof.{obj}
    MD $guns1/$guns2, Born1/Born2   -> one group per ship id built in a do_all, and one instantiated
                                       cue that carries $e (NEEDS A PROBE: event_weapon_fired
                                       must still resolve the right ship with N groups)

  Wire changes (each needs a new message version, '|2|'; v1 stays byte-identical for 2 players)
    HELLO/RESUME/WELCOME   slot field accepts p<n> and a0
    AUTH                   revision, count, count x (ship, owner, epoch, pilot)
    HGEN                   revision, count, count x (ship, gen)
    WORLD                  ship count before the per-ship triples; LAN targets in their own section
    SHOT                   victim kind + id instead of 1-2/3-4
    BOLT/BEND              entity range 1..MAX_SHIPS (projectile_protocol.py:105)
    TRADE/BUBBLE f[5]      any player id
    UINTEREST/UACK         per player (one interest set per non-authority player)
    COMMAND                ship id stays a number, the slot field stays a slot
  The roster itself reaches the clients in a ROSTER message (players, authority, ships,
  born_owner, revision) sent with AUTH. The invitation (JOIN-SESSION.json) names only the
  recipient's own player id and the authority address.

  Authority policy (listen vs dedicated)
    listen (today): authority 'p1' is also a player. The current split rules stay as they are:
      a remote pilot's world decides its ship's health while its generation is live (HBASE/HACK,
      victim_authority). This is the regression baseline.
    dedicated (Ferrite's decision: TRUE server authority): authority 'a0'; every human is a
      non-authority player. The server decides all hits and health. Clients send intent
      (NAV2/FIRE2/requests) and render. The guest-world-decides paths (health_live/HACK,
      guest-owned SHOT victims) are then unused, not extended to N. This depends on H3 (the
      server must simulate remote players' areas with attention 9).


4. MIGRATION PLAN (every step parity-gated; no behaviour change before step 4)
------------------------------------------------------------------------------
  1  Relay: add Roster with two-player defaults; replace the S1-S6 literals in x4lan/ (82 hits,
     15 files). Pure refactor: the existing test suite must pass unchanged.
  2  Lua adapter: roster helpers from config; replace cfg.slot comparisons and 'for e=1,2'
     (110 hits, 19 files). Pure refactor; LuaJIT tests unchanged.
  3  MD: replace literal .{1}/.{2} ship reads with list iteration where the semantics are plain;
     probe the per-ship weapon-group/cue question before touching projectile.xml/bubble.xml.
  4  Wire v2 (AUTH/HGEN/WORLD/SHOT victim/BOLT entity/UINTEREST/ROSTER) behind a session
     capability; synthetic three-player relay tests (fixtures with p1, p2, p3).
  5  Distinct authority 'a0' + dedicated policy, after H3 shows the server can simulate remote
     areas. Packaging roles become server/client (listen-host kept for regression).
  Each step is a separate PR; dev/h4_inventory.py run before and after shows the hits
  that are gone.


5. DECISIONS NEEDED FROM THE LEAD
---------------------------------
  Q1 MAX_PLAYERS / MAX_SHIPS for the first N-player target (suggest 4 / 8 for tests; the wire
     pattern allows 99).
  Q2 Authority id 'a0' and whether listen mode (authority == p1) stays as the regression
     baseline until dedicated mode passes H3. Recommended: keep it.
  Q3 Is section 3 the shared contract for the Python and Rust relays? Recommended: yes, so the
     parity harness can check both against one roster spec.
  Q4 LAN-target victim namespace: kind field or numeric offset.
  Q5 Should the Python steps (1-2) land before the Rust relay replaces host.py, or only
     inside the Rust relay? If Rust comes first, step 1 is done there and Python stays two-player.
